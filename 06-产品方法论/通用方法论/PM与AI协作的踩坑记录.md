# PM 与 AI 协作的踩坑记录

> **文档定位**：记录产品经理和 AI 协作过程中反复出现的错误模式和正确做法
> **来源**：从 ERP 重构项目的 AGENTS.md 踩坑记录和产品工作流文档中提取

---

## 坑 1：流程推演内容过简

**错误**：只画正常的主流程（Happy Path），忽略异常分支。

**正确做法**：
- 必须覆盖四类场景：**主流程**、**支线流程**（撤回重提、批量导入）、**辅助流程**（取消、关闭）、**异常处理**（系统故障、外部系统失败）
- 支线和辅助流程与主流程同等重要，不应放在末尾轻描淡写
- 不要为了省 Token 而简化——推演文档的价值就在于通过详细步骤暴露逻辑漏洞

---

## 坑 3：参考旧文档时未做批判性检查

**错误**：直接把旧版 Demo PRD 当"结构质量很高"并直接复用，未对照现行规范检查。

**正确做法**：
- 参考旧文档时，必须先对照**现行规范**逐项检查
- 旧文件与现行规范冲突时，以现行规范为准，主动指出并修正
- 旧文件有价值的是其**章节结构和业务内容**，不是其具体展现方式

---

## 坑 4：字段清单机械性添加冗余列

**错误**：对没有导入导出功能的模块，机械性添加"可导入""可导出"两列，所有字段填"否"。

**正确做法**：
- 「可导入」和「可导出」是**按需添加列**，只有模块已明确规划该功能时才添加
- 没有该功能就不要加该列——冗余列伤害可读性

---

## 坑 5：字段清单误归属为业务设计

**错误**：将字段清单归类为"业务设计/数据设计"产出物。

**正确做法**：字段清单描述的核心内容（控件类型、新增/编辑行为、列表展示规则、筛选组件类型）都属于**应用设计**层。业务设计的数据产出是 ER 图 + 枚举值定义（概念层），不含 UI 行为。

---

## 坑 8：列表列顺序和 Mock 枚举未与源文件逐条对账

**错误**：按 Demo PRD 修改列表页时，表头列顺序与 PRD 不一致，Mock 里出现字段清单未定义的枚举文案。

**正确做法**：
- 接列表页任务时：用 Demo PRD 的表格列从左到右与代码中的列定义**逐列核对**
- 写或改 Mock：凡带枚举语义的字段，只允许使用字段清单中已写明的取值
- PRD 变更后：至少过一遍「列顺序 + 查询字段 + 行操作矩阵」再写代码

---

## 反模式汇总

| 反模式 | 正确做法 |
| :--- | :--- |
| 先写字段清单，后补业务PRD | 业务背景先确认，PRD可以和字段清单并行 |
| 先做一版"差不多的页面"再慢慢修 | 先对齐参考页和规范，再动手 |
| 把前端原型生成当作可跳过的步骤 | 没有可点击原型，需求评审是低效的 |
