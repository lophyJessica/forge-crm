# AI 时代产品经理的系统设计方法论

> **文档定位**：本文是一套面向中后台系统的产品设计工作法，适用于「一个产品经理 + AI」协作完成业务分析、系统设计、规则定义与原型输出的场景。
>
> **核心主张**：不是让 AI 替代产品经理做判断，而是建立一套「先想清楚，再让 AI 扩写和传播」的设计秩序。
>
> **方法论立场**：借鉴传统软件工程的分层思想，但不照搬其重文档形态；强调**分层、验证、追溯、可传播**，而不是堆砌文档数量。
>
> **版本**：V2.1 | 更新时间：2026-04-15

## 与本仓库 QS-JXC 工作流方法论的关系

本文是**通用理论层**方法论；项目落地时以《QS-JXC 产品经理使用AI输出相关产出物的工作流与方法论》为准。本文的概念与 QS-JXC 实际产物对应如下：

| 本文概念 | QS-JXC 实际产物 |
| :--- | :--- |
| 业务上下文 | `01-全局背景信息/`（公司、项目、全局基线） |
| 系统骨架 | `02-需求调研/`、业务流程与系统单据流程 |
| 场景粗流程推演（验证关卡①） | 业务流程推演（按需产出，不复制进单据 PRD） |
| 字段清单 | 字段清单详细稿 TSV（字段事实源） |
| 业务规则规格 | 业务 PRD（业务规则源） |
| 用例数据推演（验证关卡②） | 按需独立生成，非固定产物 |
| 页面实现规格 | 前端 Demo PRD（页面表现与交互源） |
| 页面骨架 | 页面骨架/ASCII 线框图（可选中间产物，不进入最终链路） |

差异点：QS-JXC 简化了文档集——页面骨架为可选产物、用例数据推演按需生成、字段清单用 TSV 单载体（不维护 Markdown 副本）；其余分层权威源、变更传播、AI 边界等原则与本文一致。

## 一、先说结论

这套方法论的核心，浓缩为三句话：

1. **产品设计必须分层推进，但分层不等于瀑布。** 每一层做到"够用"就进入下一层，发现矛盾随时回溯——分层是为了理清思路，不是制造流程包袱。

2. **不存在一份万能文档覆盖所有信息，只有「分层权威源」。** 不同类型的信息（业务目标、系统骨架、模块规则、页面交互）各有归属，每一类信息有且只有一个权威定义位置。

3. **PM 做判断，AI 做传播。** AI 最擅长的是结构化整理、下游文档生成、一致性校验；业务规则的裁定、优先级的取舍、边界场景的确认——这些必须由人来做。

把三句话合成一段：

> 产品经理先定义业务目标、系统边界和关键规则，再让 AI 基于这些上游权威源生成下游文档、页面规格和前端原型。任何下游问题，都应回溯到对应层级的源头修正，而不是在生成物上长期打补丁。

## 二、这套方法论从哪来

它不是理论推导的产物，而是在一个真实的 ERP 重构项目中踩了足够多的坑之后，被逼出来的。

项目初期，我们摸索出一套以**字段清单为核心**的文档输出方法：字段清单 → PRD → Demo PRD → 前端原型。这套方法解决了"一个 PM 如何高效输出一致的需求文档"的问题，效率确实很高。

但随着模块增多，问题开始暴露：

| 踩过的坑 | 具体表现 |
| :--- | :--- |
| **缺全局视角** | 每个模块有自己的字段和页面，但没有一张图把所有模块串起来，系统全貌看不到 |
| **顺序倒了** | 先画页面再补流程，发现走不通时返工量大 |
| **规则到处散落** | 业务决策混在聊天记录、项目规范文件、字段备注里，找不到也对不齐 |
| **文档自相矛盾** | 字段清单说一套，PRD 说一套，原型又是一套 |

对照传统软件工程的分层设计思想（需求设计 → 业务设计 → 应用设计 → 技术设计），我们发现：**模块级设计做得不错，但全局级设计（业务流程、系统架构、需求分析）几乎是缺位的。**

传统的全套产出物是为一个完整团队设计的——有需求分析师、产品经理、UX 设计师、技术文档工程师各司其职。一个 PM + AI 的模式照搬不现实。于是问题变成了：**如何在保留分层思想的前提下，设计一套适合 PM + AI 协作的轻量方法论？**

这就是本文的来历。

## 三、它解决什么问题

在 ERP、WMS、CRM 等中后台项目里，常见问题不是"不会写 PRD"，而是设计顺序和信息结构出了问题：

| 问题 | 典型表现 | 对应解法 |
| :--- | :--- | :--- |
| 宏观缺失 | 模块都有字段和页面，但系统全貌不清楚 | 先做业务上下文和系统骨架 |
| 顺序倒置 | 先画页面后补流程，返工量大 | 先用粗流程验证，再进入模块设计 |
| 规则散落 | 业务规则混在聊天、规范文件、字段备注里 | 明确规则归档原则——什么规则写在哪里 |
| 文档打架 | 字段清单、PRD、原型说法不一致 | 建立分层权威源和传播规则 |
| PM 重复写作 | 同一件事在多份文档里手工重复 | AI 负责扩写与下游文档生成 |

## 四、适用范围与边界

### 4.1 适用场景

- ERP、WMS、CRM、供应链、财务协同等中后台系统
- 以「流程 + 单据 + 主数据 + 规则」为核心的业务系统
- 产品经理需要与 AI IDE 长期协作，持续生成文档和原型

### 4.2 不适用场景

- **强探索型产品**：连核心问题和目标用户都没收敛——先做用户验证，再谈设计方法论
- **纯 To-C 增长型产品**：更依赖实验、埋点、转化漏斗和 A/B Test，不以单据流程为核心
- **纯技术改造项目**：如性能优化、底层迁移、基础设施升级——没有业务流程建模的需求

### 4.3 适用前提

- PM 对业务至少有基础理解（完全陌生的领域，先做调研再进入本方法论）
- 业务方愿意确认关键决策
- 团队接受"先定义上游，再生成下游"的工作方式

## 五、核心原则

### 5.1 分层推进，但不是瀑布

设计必须从宏观到微观推进，但各层之间不是一次性流过，而是**循环校正**。

正确理解：
> 先做到大概对 → 进入下一层 → 发现矛盾就回溯 → 修正后继续向下

错误理解：
> 上一层完全做完 → 永不回头 → 机械进入下一层

分层的目的是**理清思路**，不是制造流程枷锁。

### 5.2 不是单一 SST，而是分层权威源

一个系统里，不同类型的信息应该由不同文档负责——不能强行让一份文档定义一切。

| 信息类型 | 权威源 |
| :--- | :--- |
| 业务目标、范围、关键决策 | 业务上下文 |
| 跨模块实体关系、模块边界、共享机制 | 系统骨架 |
| 场景流转和异常分支 | 场景流程推演 |
| 模块字段事实 | 字段清单 |
| 模块状态机、权限、校验、计算规则 | 业务规则规格 |
| 页面布局、控件形态、交互细节 | 页面实现规格 |

> **每一类信息有且只有一个权威归属位置。** 改一条业务规则，去业务规则规格里改；改一个字段定义，去字段清单里改。不管这条信息在多少份下游文档里出现过，**源头只有一个**。

### 5.3 先粗后细，两道验证关卡

很多项目出问题，不是因为字段没列全，而是因为**在还没验证业务能不能跑通时，就开始细化页面了**。

本方法论设置两道验证关卡：

1. **粗流程验证**（宏观层底部）：验证场景是否闭环、上下游是否接得住、关键异常分支是否存在
2. **用例数据推演**（中观层底部）：带着具体的字段值、状态流转、金额计算，把流程走一遍——"逻辑看上去能走"和"带着真实数据仍然能走"是两件事

过不了验证关卡，不往下走。

### 5.4 规则必须归位

规则不怕多，怕混。

最常见的错误不是规则缺失，而是规则放错了地方：

- 业务决策写在了项目规范文件里
- 模块规则塞进了字段备注
- 共享机制混在某一个模块的规则文档里
- 页面级交互规则反过来覆盖了上游业务规则

**先决定「这条规则属于哪一层」，再决定写在哪里。**

### 5.5 PM 做判断，AI 做扩写

PM 的核心价值是**判断力**——裁定业务规则、明确边界和优先级、决定取舍。这些是 AI 无法替代的。

AI 的核心价值是**生产力**——结构化整理、扩写下游文档、扫描一致性问题、生成原型和演示材料。

> PM 的稀缺资源是判断力，不是写作时间。方法论的每一步都应该最大化 PM 的思考时间，最小化 PM 的文档编写时间。

## 六、三层模型

本方法论将设计工作分为三层——**宏观、中观、微观**——每一层回答不同粒度的问题。

| 层级 | 回答的问题 | 思考对象 | 举例 |
| :--- | :--- | :--- | :--- |
| **宏观层** | 业务从头到尾怎么流转？涉及哪些角色和环节？系统整体怎么组织？ | 业务流程、系统边界、模块关系、共享机制 | "采购员下单 → 审核 → 通知仓库 → 收货 → 入库" |
| **中观层** | 某个模块有哪些数据、遵循什么规则？ | 字段、状态机、业务规则、校验逻辑 | "采购订单有 20 个字段，状态从草稿到已审核需要……" |
| **微观层** | 页面上每个控件长什么样、交互怎么做？ | 控件类型、布局、显隐条件、按钮位置 | "供应商字段用 SelectWithSearch，放在第一行第二列" |

**核心原则：先宏观，后中观，最后微观。**

宏观层的产出是中观层的**输入**——先知道"业务怎么流转"，才能决定"这个模块需要哪些字段和规则"。中观层的产出是微观层的**输入**——先知道"有哪些字段和规则"，才能决定"页面长什么样"。

顺序倒过来，就会出现"页面都做完了才发现流程走不通"的返工。

### 文档层级与权威源规则

| 层级 | 文档 | 谁维护 | 权威源管辖范围 |
| :--- | :--- | :--- | :--- |
| **宏观** | 业务上下文（按域） | PM 编写 | 业务范围、关键决策的权威源 |
| **宏观** | 系统骨架（实体图 / 模块图 / 共享机制） | PM 定义 + AI 画图 | 系统全局结构的权威源 |
| **宏观** | 场景粗流程推演（按场景） | AI 生成 + PM 审核 | 业务流程逻辑的权威源 |
| **中观** | 字段清单（按模块） | PM 维护 | 字段定义的权威源 |
| **中观** | 业务规则规格（按模块） | PM 维护 | 业务规则和状态机的权威源 |
| **中观** | 用例数据推演（按模块/场景） | AI 生成 + PM 审核 | 数据验证的权威源 |
| **微观** | 页面实现规格（按页面） | AI 生成 + PM 审核 | 生成物，不是权威源 |
| **微观** | 前端原型 | AI 生成 | 生成物，不是权威源 |

**层级规则**：

1. **上游优先**：两份文档冲突时，层级高的赢
2. **向下生成**：上游变更后，所有受影响的下游文档需要重新生成
3. **向上追溯**：下游发现问题时，修改源头文档，然后重新生成下游
4. **同层互参**：同一层级的文档互相引用但不互相定义（例如业务规则规格引用字段清单中的字段名称，但不重复定义字段本体）

## 七、推荐产物体系

### 7.1 宏观层：业务上下文

**目的**：回答"为什么做"和"业务方已经确认了什么"。

按**业务域**维护，一域一份。一个业务域涵盖一组紧密关联的业务模块（如"采购域"涵盖采购订单、收货通知、采购入库等）。

**建议包含**：

| 模块 | 内容 |
| :--- | :--- |
| 业务背景 | 现状、痛点、角色、目标 |
| 范围定义 | 本期做、不做、待确认 |
| 关键业务决策 | 结论、依据、确认人、确认日期 |
| 设计目标与约束 | 性能、合规、接口、组织边界、上线节奏 |
| 与其他业务域关系 | 上游输入、下游输出、边界说明 |
| 变更记录 | 重要变更与影响范围 |

**最小模板**：

```markdown
# [业务域名称] · 业务上下文

## 业务背景
- 涉及角色：XX部门、XX岗位
- 现状描述：目前如何运作（系统/手工/混合）
- 核心痛点：①... ②... ③...

## 业务范围
| 范围 | 内容 |
| :--- | :--- |
| 本期做 | ... |
| 不做 / 后期做 | ... |
| 待确认 | ... |

## 关键业务决策
| 决策事项 | 结论 | 决策依据 | 确认人 | 确认日期 |
| :--- | :--- | :--- | :--- | :--- |
| ... | ... | ... | ... | ... |

## 与其他业务域的关系
- 上游：...（提供什么数据/触发什么流程）
- 下游：...（输出什么数据/触发什么流程）

## 变更记录
| 日期 | 变更内容 | 影响范围 |
| :--- | :--- | :--- |
```

**边界提醒**：这里不定义字段明细、不画页面布局、不写状态机。它只回答"做什么、为什么做、业务方确认了什么"。「关键业务决策」表格是这份文档的核心价值——提供**决策可追溯性**。

---

### 7.2 宏观层：系统骨架

系统骨架负责建立"系统全貌"，建议拆成三类文档。

#### ① 业务实体关系

回答"系统里有哪些核心对象，它们是什么关系"。

对象可以包括：主数据、业务单据、通知单、结果单、结算对象、外部系统对象。

建议产出一张 Mermaid ER 图 + 一份实体清单表格：

```markdown
## 实体清单
| 实体 | 所属域 | 类型 | 说明 |
| :--- | :--- | :--- | :--- |
| 采购订单 | 采购 | 业务单 | 采购意图的载体 |
| 收货通知单 | 采购 | 通知单 | 指导仓库执行收货 |
| 采购入库单 | 库存 | 结果单 | 收货完成后的凭证 |
```

#### ② 模块关系与流转

回答"模块之间如何联动"。至少说清：上下游关系、触发条件、字段继承原则、回传方式、是否允许逆向处理。

```markdown
## 单据联动规则
| 上游单据 | 动作 | 下游单据 | 触发条件 | 字段继承 |
| :--- | :--- | :--- | :--- | :--- |
| 采购订单 | 下推 | 收货通知单 | 审核通过 | 继承供应商、商品明细 |
| 收货通知单 | 回传生成 | 采购入库单 | WMS回传 | 继承通知数量，实收来自WMS |
```

#### ③ 共享机制

回答"哪些规则不是某一个模块私有的，而是多个模块共用的"。

典型包括：审批机制、单据编号规则、价格查询机制、权限控制模型、日志与通知机制、外部系统回传机制。

> 经验之谈：当你发现一条规则被三个以上模块引用时，就应该把它从模块文档中提取到共享机制文档中。否则改一处、漏三处。

---

### 7.3 宏观层：场景流程推演（验证关卡 ①）

这是从"系统骨架"进入"模块设计"前的**第一道验证**。

它的任务不是细化字段，而是验证：业务场景端到端能不能走通、关键角色有没有覆盖、关键异常分支存不存在、上下游单据能不能接上。

按**业务场景**维护，一场景一份。每份至少覆盖：

| 项目 | 说明 |
| :--- | :--- |
| 场景目标 | 这个场景解决什么业务问题 |
| 参与角色 | 谁发起、谁处理、谁确认 |
| 前置条件 | 进入场景前需要满足什么 |
| 主流程 | 正常路径，按步骤和泳道展示 |
| 关键异常 | 驳回、撤回、取消、部分完成、失败回传 |
| 结束状态 | 场景何时算结束 |
| 跨模块联动 | 涉及哪些模块和数据流 |

**重要区分**：粗流程推演不要求字段级精确，但**必须带着关键规则意识推进**。比如"是否允许部分收货"这种判断，已经涉及规则设计，不应等到画页面时才发现。它是**设计验证**，不是故事会。

> ⛔ **关卡规则**：如果核心场景走不通——比如上下游单据接不上、关键异常分支没有处理方案——就回到业务上下文或系统骨架调整，不要硬往下走。

---

### 7.4 中观层：字段清单

字段清单的职责很单纯：

> 定义一个模块有哪些字段，以及这些字段的基础事实。

按**模块**维护，每模块一份。建议负责以下内容：

- 字段名称、数据类型、必填性
- 枚举值、来源方式、默认值
- 展示口径（列表/详情/新增/编辑各展示什么）
- 是否计算字段、计算公式

**字段清单不宜承担**的内容：完整状态机、完整权限矩阵、大段业务规则、页面布局说明。

> 字段清单是「模块数据事实的权威源」，不是模块设计的全部。它回答"有什么数据"，不回答"数据怎么运转"。

**与流程推演的衔接**：流程推演在宏观层已经隐含了字段需求。例如推演中写到"采购员选择供应商、输入交货日期、添加商品明细"，就意味着字段清单需要包含"供应商""交货日期""商品明细"等字段。字段清单的工作是把这些**隐含的数据需求显式化、规格化**。

---

### 7.5 中观层：业务规则规格

如果字段清单回答"有什么"，那业务规则规格回答"怎么运转"。

复杂模块建议单独维护一份。简单模块的规则可以直接写在字段清单的说明列中，不必强行拆文件。

**建议包含**：

| 模块 | 内容 |
| :--- | :--- |
| 状态机 | 状态定义、流转条件、终态 |
| 动作矩阵 | 谁在什么状态下能做什么 |
| 校验规则 | 前置校验、提交校验、审核校验 |
| 权限规则 | 按角色、组织、数据范围控制 |
| 计算规则 | 金额、数量、税额等 |
| 逆向规则 | 撤回、作废、关闭、红冲、反审 |
| 对外联动规则 | 下推、回传、同步、补偿 |

> **为什么不叫"业务主PRD"？** 因为它本质上不是广义的产品需求文档，而是模块级规则的权威定义。叫"业务规则规格"能更准确地传达它的职责边界，避免与传统 PRD 的概念混淆。

**验证回路**：写规则规格时可能发现字段清单漏字段 → 回字段清单补充。规则规格的状态机可能与宏观层的流程推演矛盾 → 协商后修改其中一方。这是正常的迭代，不是流程失败。

---

### 7.6 中观层：用例数据推演（验证关卡 ②）

这是**第二道验证**，也是很多中后台项目文档体系最容易缺的一环。

为什么它重要：只有把具体数据代入流程，很多隐藏问题才会暴露。"逻辑看上去能走"和"带着数据仍然能走"是两件事——金额对不对、状态闭不闭、字段接不接得上，都需要用真实数据验证。

建议至少推演以下案例：

| 案例类型 | 验证目标 |
| :--- | :--- |
| 正常案例 | 主流程、金额计算、状态流转 |
| 部分完成案例 | 部分收货/部分发货场景的数据正确性 |
| 异常中断案例 | 取消/驳回/撤回后的数据一致性 |
| 逆向处理案例 | 红冲/反审核后的状态和数量回滚 |
| 跨组织/跨系统案例 | 多组织场景下的数据隔离和联动 |

> 如果粗流程验证是"故事走得通"，那用例数据推演就是"**账算得平，状态闭得住，字段接得上**"。

> ⛔ **关卡规则**：如果账算不平或状态闭不住，回到字段清单或业务规则规格修正，必要时回到宏观层的流程推演重新审视。

---

### 7.7 微观层：页面实现规格

到这一层才进入"页面怎么呈现"。

它的职责是：页面结构、查询区/表格区/详情区布局、控件类型、显隐条件、动作入口、交互反馈、前端演示需要的 mock 口径。

> **为什么不叫"Demo PRD"？** 同理，叫"页面实现规格"能更清楚地表达它的职责——描述页面如何承载上游的模块设计——避免与上游的业务规则规格混淆。

**核心约束**：页面实现规格是**生成物**，由 AI 基于字段清单 + 业务规则规格生成，PM 审核。源文件变化后应重新生成。**严禁在页面规格中反向定义或覆盖上游的业务规则和字段定义。**

---

### 7.8 微观层：前端原型

原型的职责是验证交互是否合理、页面结构是否顺畅、演示效果是否达标、业务方是否容易理解。

原型不是业务权威源，也不是规则权威源。它只能证明"看起来像能用"，**不能替代规则设计**。

---

## 八、推荐工作流

六个步骤，从宏观到微观，两道验证关卡穿插其中。

### 全流程一览

```
宏观层 ─────────────────────────────────────────────────────
  ① 业务上下文         "为什么做、做什么范围"
  ② 系统骨架           "有哪些模块、模块之间怎么连"
  ③ 场景粗流程推演      "业务从头到尾怎么走"  ← 验证关卡 ①
                         ↓ 走不通？→ 回①②调整
中观层 ─────────────────────────────────────────────────────
  ④ 字段清单 + 业务规则规格    "每个模块有什么数据、遵循什么规则"
  ⑤ 用例数据推演               "带着数据跑一遍"  ← 验证关卡 ②
                                ↓ 跑不通？→ 回④或③调整
微观层 ─────────────────────────────────────────────────────
  ⑥ 页面实现规格 + 前端原型    "页面怎么承载、可运行演示"
```

### 分步说明

#### 第一步：业务上下文

| 维度 | 说明 |
| :--- | :--- |
| **产出** | 业务上下文（按域） |
| **PM 做** | 与业务方沟通，编写文档 |
| **AI 做** | 辅助整理结构、提炼表达 |
| **完成标志** | 本期范围明确、关键决策有记录、主要约束已写明 |

#### 第二步：系统骨架

| 维度 | 说明 |
| :--- | :--- |
| **产出** | 业务实体关系、模块关系与流转、共享机制 |
| **PM 做** | 定义模块边界、确认联动逻辑 |
| **AI 做** | 画 Mermaid 图、梳理遗漏 |
| **完成标志** | 模块边界清楚、数据主流向清楚、共性机制不挂空 |

#### 第三步：场景粗流程验证 ← 验证关卡 ①

| 维度 | 说明 |
| :--- | :--- |
| **产出** | 场景粗流程推演（按场景） |
| **PM 做** | 提供场景描述和关键规则，审核推演结果 |
| **AI 做** | 生成完整流程推演（含异常分支和跨模块联动） |
| **完成标志** | 核心场景闭环、关键异常已覆盖、跨模块联动成立 |

> ⛔ 流程走不通，回到第一步或第二步调整。

#### 第四步：字段清单 + 业务规则规格

| 维度 | 说明 |
| :--- | :--- |
| **产出** | 字段清单 + 业务规则规格（按模块） |
| **PM 做** | 定义字段、状态机、校验规则、权限 |
| **AI 做** | 生成字段清单初稿、对照检查一致性 |
| **完成标志** | 字段完整、状态机闭环、校验/权限/逆向规则明确 |

#### 第五步：用例数据精校验 ← 验证关卡 ②

| 维度 | 说明 |
| :--- | :--- |
| **产出** | 用例数据推演 |
| **PM 做** | 审核数据是否跑得通 |
| **AI 做** | 代入模拟数据推演全流程 |
| **完成标志** | 关键场景可代入真实数据跑通、状态/数量/金额不打架 |

> ⛔ 账算不平或状态闭不住，回到第四步甚至第三步修正。

#### 第六步：页面实现与原型生成

| 维度 | 说明 |
| :--- | :--- |
| **产出** | 页面实现规格 + 前端原型 |
| **PM 做** | 审核页面是否正确承载了上游设计 |
| **AI 做** | 生成页面规格和可运行原型 |
| **完成标志** | 页面与上游规则一致、交互可演示、不出现页面反向定义业务 |

### 执行速查表

| 步骤 | 产出物 | 层级 | PM 做 | AI 做 | 完成标志 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| ① | 业务上下文（按域） | 宏观 | 编写 | 辅助整理 | 业务方确认关键决策 |
| ② | 系统骨架（实体图/模块图/共享机制） | 宏观 | 定义 | 画图 | 模块边界和数据流向明确 |
| ③ | 场景粗流程推演（按场景） | 宏观 | 审核 | 生成 | 全部场景（含异常）走通 |
| ④ | 字段清单 + 业务规则规格（按模块） | 中观 | 维护 | 生成初稿 | 字段完整、规则闭环 |
| ⑤ | 用例数据推演 | 中观 | 审核 | 生成 | 数据跑通、状态自洽 |
| ⑥ | 页面实现规格 + 前端原型 | 微观 | 审核 | 生成 | 页面可运行、交互正确 |

## 九、变更传播原则

### 9.1 总原则

> 不是"所有问题都回到最上游"，而是**回到受影响的最高权威层**。

### 9.2 变更场景举例

| 变更场景 | 从哪改（源头） | 影响范围（向下传播） |
| :--- | :--- | :--- |
| 业务方说"配销订单要支持跨组织" | ① 业务上下文 + ② 模块关系图 | → ③ 流程推演 → ④ 字段清单、规则规格 → ⑥ 页面全部重新生成 |
| 流程推演发现"缺少取消收货的分支" | ③ 流程推演 → 回溯 ① 确认业务规则 | → ④ 补充相关字段和状态 → ⑥ 重新生成 |
| 新增一个字段"物流单号" | ④ 字段清单 | → 规则规格可能补规则 → ⑥ 重新生成。①②③ 不用动 |
| 页面上按钮位置不对 | ⑥ 页面实现规格（微调） | 只影响原型。上游不用动 |
| 审批流统一改成三级审批 | ② 共享机制设计 | → 所有涉及审批的模块的规则规格更新 → ⑥ 重新生成 |

### 9.3 三条铁律

1. **永远改源头，不改生成物**：发现页面规格的字段定义不对，去改字段清单，然后重新生成页面规格
2. **向上追溯到发生变更的最高层级**：如果问题出在业务逻辑层面，不要只改字段清单，要追溯到流程推演甚至业务上下文
3. **下游可以微调，但不可矛盾**：页面规格可以调整布局和控件选型（微观层面的优化），但不能改变字段定义或业务规则。如果微调持续触及上游定义，说明需要上溯修正

## 十、规则归档原则

这是整套方法里最容易乱的地方。用一张表把它钉死：

| 规则类型 | 应归档位置 | 举例 |
| :--- | :--- | :--- |
| 业务背景和决策 | 业务上下文 | "是否允许门店直送" |
| 跨模块通用机制 | 共享机制 | 审批流、编号规则、价格查询 |
| 场景级流转逻辑 | 场景粗流程推演 | "收货失败后是否允许重试" |
| 模块内状态与动作规则 | 业务规则规格 | "草稿能否直接审核、已审能否关闭" |
| 字段基础属性 | 字段清单 | 类型、必填、枚举、来源 |
| 页面交互细节 | 页面实现规格 | 按钮位置、控件形态、展开收起 |
| 项目协作规范 | 项目规范文件 | 命名规范、目录规则、前端基线 |

> **注意**：项目规范文件适合放协作规范，不适合长期承载业务真相；字段清单适合放字段事实，不适合承载整套模块规则；页面规格适合放呈现方式，不适合定义业务语义。每种文档守好自己的边界。

## 十一、AI 的角色与边界

### 各层分工

| 层级 | PM 负责 | AI 负责 |
| :--- | :--- | :--- |
| 宏观层 | 访谈、判断、确认边界 | 整理记录、提炼结构、画图、梳理场景、检查遗漏 |
| 中观层 | 决定字段、状态、规则 | 生成初稿、对照检查一致性、代入数据推演 |
| 微观层 | 审核页面是否承载正确 | 生成页面规格、原型、演示数据 |

### 什么不能交给 AI

无论方法论如何优化，以下内容**必须 PM 亲自把关**，不能依赖 AI 的判断：

1. **业务规则的最终裁定**：中后台业务逻辑有行业和企业特殊性，AI 无法判断"这个规则是否合理"
2. **功能优先级决策**：做不做、先做哪个，是产品策略判断，不是逻辑推理
3. **边界情况的业务确认**：异常分支的处理方式（取消？关闭？红冲？），答案必须来自业务方
4. **跨业务域的取舍**：当两个域的需求冲突时，选哪个、怎么折中，是产品决策
5. **AI 产出物的审核**：AI 生成的每一份文档都可能有错误，PM 是最后一道质量关

> **一句话总结**：AI 最大的价值是把产品经理从"把想清楚的东西写清楚"中解放出来，让你有更多时间"把事情想清楚"。**想的部分不能省，写的部分可以让 AI 帮你。**

## 十二、常见误区

### 误区 1：字段清单就是一切

字段清单只能回答"有什么数据"。它回答不了：流程为什么这么走、规则为什么这么定、异常怎么处理、跨模块为什么这样联动。字段清单很重要，但它只是中观层的一半。

### 误区 2：流程推演不需要带规则

粗流程推演不要求字段级精确，但**必须带着关键规则意识推进**。"是否允许部分收货""缺收后能否在原单补发"——这些在流程层就要有答案，不能等到写字段时才想。

### 误区 3：页面能跑就说明设计没问题

这是最危险的误区。页面能跑只能证明前端原型闭合，不代表：业务闭环成立、状态机自洽、对账关系正确、异常和逆向规则能自圆其说。

### 误区 4：AI 生成越多文档越好

文档数量不是价值本身。真正有价值的是：上游是否稳定、权威源是否清楚、下游是否一致。三份高质量的上游文档，胜过二十份自相矛盾的 PRD。

## 十三、与传统软件工程的关系

本方法论不是凭空发明的，它和传统软件工程有明确的继承关系：

| 传统概念 | 本方法论的对应 |
| :--- | :--- |
| 需求设计（需求分析） | → 宏观层：业务上下文 |
| 业务设计（业务架构 + 流程 + 数据） | → 宏观层：系统骨架 + 场景粗流程推演 |
| 应用设计（组件 + 界面 + 机制） | → 中观层：字段清单 + 业务规则规格 + 共享机制 |
| 技术设计 | 不在 PM 职责范围内，交由研发 |
| PRD（综合交付物） | → 微观层：页面实现规格 |

**借鉴了什么**：分层思考的必要性、先理解业务再设计系统、人类判断的不可替代性。

**改变了什么**：

| 维度 | 传统方式 | PM + AI 方式 |
| :--- | :--- | :--- |
| 文档维护 | 每份文档独立编写和维护 | 分层权威源：源头手动维护，下游 AI 生成 |
| 分工模式 | 需求分析师 + PM + UX + 技术文档工程师 | 一个 PM 做决策 + AI 做文档生成和一致性检查 |
| 产出物重量 | 完整的 SRS、业务设计文档、应用设计规格书…… | 轻量化：关键图 + 结构化表格 + 生成的规格文档 |
| 迭代成本 | 改一处，手动同步 N 份文档 | 改源头，AI 重新生成所有下游 |

## 十四、优势与局限性

### 优势

| 优势 | 说明 |
| :--- | :--- |
| **一个人能完成** | PM 专注决策，AI 处理文档生成和格式化，不需要完整的产品团队 |
| **顺序清晰** | 六步从宏观到微观，每一步都有明确的输入和输出 |
| **返工成本低** | 分层权威源 + 向下生成机制保证"改一处更新全部" |
| **验证前置** | 两道验证关卡在早期发现问题，避免到微观层才发现流程不通 |
| **AI 友好** | 所有文档用 Markdown + Mermaid，AI 可以直接消费和生成 |
| **可追溯** | 每个设计决策都能追溯到业务上下文中的确认记录 |

### 局限性

坦诚讲，这套方法论不是万能的：

| 局限 | 说明 | 缓解方式 |
| :--- | :--- | :--- |
| **依赖 PM 的业务判断力** | AI 无法判断业务规则是否合理，PM 的业务理解深度决定产出质量 | PM 必须充分与业务方沟通，不能只靠 AI 推理 |
| **宏观层的初始投入** | 业务上下文和系统骨架需要前期投入时间 | 可以先做粗粒度版本，随着模块设计逐步细化 |
| **不适合全新领域** | 如果 PM 对业务领域完全陌生，无法在第一步提供有效的业务上下文 | 先做调研（访谈、竞品分析），再进入本方法论 |
| **跨团队协作未覆盖** | 本方法论为"一个 PM + AI"设计，多 PM 协作、PM 与研发的协作流程未纳入 | 需要额外定义协作规范和文档评审机制 |
| **AI 生成物可能有错** | AI 生成的页面规格和原型可能有遗漏或错误 | PM 必须审核每一份生成物，不能直接交付 |

## 十五、文档规模估算与最小可执行版本

### 规模估算

以一个包含 5 个业务域、20 个模块的中后台系统为例：

| 层级 | 文档数量 | PM 维护成本 |
| :--- | :--- | :--- |
| 宏观层 | ~10 份（5 份业务上下文 + 3 份骨架文档 + 若干场景推演） | 低（写一次，偶尔更新） |
| 中观层 | ~40 份（每模块字段清单 + 规则规格 + 用例推演） | 中（核心工作量） |
| 微观层 | ~80 份（每模块 3~4 份页面规格和原型） | 极低（AI 生成，PM 审核） |
| **合计** | **~130 份** | **PM 真正手动维护约 50 份，其余由 AI 生成** |

### 最小可执行版本

如果一开始不想铺太大，可以只落最小版本：

1. 每个业务域写一份「业务上下文」
2. 全项目三份骨架文档：「实体关系」「模块流转」「共享机制」
3. 每个核心场景写一份「粗流程推演」
4. 每个模块写一份「字段清单」
5. 每个复杂模块写一份「业务规则规格」
6. 每个关键模块至少做一份「用例数据推演」
7. 页面侧生成「页面实现规格 + 前端原型」

这已经足够支撑大多数中后台系统的 PM + AI 协作。

## 十六、新业务域接入 Checklist

当团队启动一个新的业务域时，按以下顺序执行：

**宏观层**
- [ ] 与业务方完成至少一轮深度沟通，记录痛点和关键诉求
- [ ] 输出「业务上下文」文档，包含业务背景、范围、关键决策
- [ ] 更新「业务实体关系图」，补充新域涉及的实体
- [ ] 更新「模块关系与单据流转图」，标注新模块与现有模块的关系
- [ ] 识别是否涉及新的共享机制，更新「共享机制设计」
- [ ] 输出核心场景的「场景粗流程推演」，覆盖正常流程和关键异常分支
- [ ] ⛔ **验证关卡 ①**：流程推演经 PM 审核确认，场景闭环后再往下走

**中观层**
- [ ] 按模块输出「字段清单」
- [ ] 按模块输出「业务规则规格」（复杂模块）
- [ ] 至少对关键模块做一轮「用例数据推演」
- [ ] ⛔ **验证关卡 ②**：数据推演跑通后再进入微观层

**微观层**
- [ ] 生成「页面实现规格」
- [ ] 生成「前端原型」

**跨模块验证**
- [ ] 检查新模块与已有模块的字段映射和状态联动是否一致
- [ ] 检查共享机制（审批、编号等）是否正常覆盖新模块

## 十七、最终定义

如果要给这套方法论下一个定义：

> AI 时代的产品经理系统设计方法论，不是"让 AI 帮你写更多文档"，而是先建立分层权威源，再用 AI 把这些权威信息稳定地扩写、传播到规则规格、页面规格和前端原型中，并通过粗流程验证与用例数据推演，持续保证设计闭环。

再压缩成一句话：

> **PM 决定真相，AI 负责传播。先验证结构，再生成页面。**
