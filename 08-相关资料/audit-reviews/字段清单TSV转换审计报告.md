## 一、总评

### 1. 结论

6 个新 TSV 的制表符列数均严格为 13，表头与标准完全一致，行本身不存在列错位问题。但“13 列结构合格”不等于“转换质量合格”：

- 商机：部分技术字段折叠到业务字段备注是有效的，但 ERP 订单同步结果字段集 5 项完全遗漏；另有 2 个明确类型错误。
- 客户：TSV 只覆盖了 16 个业务展示/聚合字段，漏掉 `crmCustomerId`、独立的 `erpCustomerId` 以及 11 个快照同步元数据字段，不能作为客户快照的唯一字段事实源。
- 合同：49 个显式字段行基本完整，来源、取值、必填性、列表/筛选/详情信息基本保留；但多处类型推断不准确，且源 Markdown 没有“字段说明/新增页/编辑页/备注”列，导致 TSV 这些列整体为空。
- 业绩目标：75 个源字段名全部进入 TSV，但源 Markdown 的章节规则没有被投影到“字段说明/取值说明”等详细列，TSV 更像 4 列字段索引，不足以承担确认后的详细字段事实源；计数、差异、版本、失败原因等类型还存在明显问题。
- 公海：显式列表字段 8 项均覆盖，但“继承线索所有列表字段”的 Markdown 叙述与列举表不一致；继承字段的类型也没有沿用线索标准。
- 拜访：TSV 实际沿用已废弃的 V1.0 `.md`，不是 V2.0 `.md_dupe` 的转换结果。若 V2.0 才是当前口径，当前 TSV 缺失执行、反馈、关联、异常和审计字段，不能使用。

## 二、逐模块问题清单

### 2.1 商机管理

对照文件：`商机字段清单.md`（源字段 33 项）与 `商机字段清单（详细稿）.tsv`（16 行）。

#### P1

1. **ERP 订单同步结果字段集完全遗漏。** Markdown 第 66-76 行定义的 5 个字段均未出现在 TSV，也没有折叠进其他业务字段的备注：`ERP_ORDER_SYNC_STATUS`、`ERP_ORDER_ID`、`ERP_ORDER_SYNC_ERROR`、`ERP_ORDER_SYNC_TIME`、`ERP_ORDER_IDEMPOTENCY_KEY`。这会使赢单后的同步状态、订单草稿编号、失败原因、同步时间和幂等重试无法从 TSV 生成。
2. **`输单原因` 类型错误。** TSV 第 11 行当前为 `单选`，但源 Markdown 第 25 行使用 `Textarea`，应为 `多行文本`。它没有给出受控枚举，不能按单选处理。
3. **`quantity` 类型错误。** TSV 第 17 行当前为 `文本`，源 Markdown 第 51 行明确为 `NumberInput`、正数且支持 2 位小数，应为 `数字`。

#### P2

4. **类型标签未完全收敛到标准值。** TSV 第 6 行 `商机阶段` 使用 `单选(枚举)`；线索标准使用 `单选`。业务语义是单选没有问题，但详细稿类型值应统一为 `单选`，避免下游按字符串匹配时出现两套类型。

#### 技术字段收敛核对

- `关联客户` 备注完整收敛了 `crmCustomerId`、`erpCustomerId`、`customerSnapshotVersion`、`customerSnapshotSyncTime`，未发现重复。
- `关联商品` 备注完整收敛了 `erpProductId`、`productCode`、`productNameSnapshot`、`unitPriceSnapshot`、`lineAmount`、`priceVersion`、`availabilityStatus`，未发现重复。
- `合同编号` 备注收敛了 `CONTRACT_LINK_STATUS`，未发现重复。
- 只有上述 12 个技术/子对象字段完成折叠；ERP 订单同步 5 项未收敛，属于 P1 遗漏。

### 2.2 客户管理

对照文件：`客户字段清单.md`（源字段 29 项）与 `客户字段清单（详细稿）.tsv`（16 行）。

#### P0

1. **客户身份与同步元数据没有完整进入 TSV。** 源 Markdown 第 12-13、38-48 行的 13 个字段未作为 TSV 字段行，也未在所属业务字段的“备注”列完整收敛：
   `crmCustomerId`、`erpCustomerId`、`snapshotVersion`、`snapshotUpdatedAt`、`sourceVersion`、`lastSuccessfulSyncAt`、`lastAttemptAt`、`syncStatus`、`syncErrorCode`、`syncErrorMessage`、`sourceEventId`、`retryCount`、`erpCustomerStatus`。
   TSV 的“客户编号”字段说明只写了“值等同 `erpCustomerId`”，这只是别名说明，不等于保留跨系统字段、快照版本、乱序保护、幂等和失败状态。若详细稿要成为 SSOT，该缺口必须先补齐。

#### P1

2. **类型推断存在多项数值/枚举错误。** 具体见“类型错误明细表”：行业、客户等级、信用额度、关联商机数、AI 流失风险、关联订单数均被推成了不合适的 `文本`；其中数量和金额相关字段会直接影响筛选、展示和计算。
3. **`客户编号`与 ERP 技术标识的关系没有按技术字段规则收口。** 源文件同时存在 `客户编号`、`erpCustomerId`、`crmCustomerId`；当前 TSV 只保留中文展示字段，且把 `erpCustomerId` 放进字段说明而非备注，未说明 CRM 内部外键应使用 `crmCustomerId`、跨系统调用应使用 `erpCustomerId`。这不是简单的同名重复，而是身份模型未完成投影。

#### P2

4. **源表列少导致大量空列。** 16 行中“必填性/新增页/编辑页/取值说明/备注”均为 16 行全空；“可筛选”有 6 行空。源 Markdown 的客户快照表只定义了来源、列表、筛选、详情和说明，未定义这些页面字段。空列是源结构不足的结果，不应自动脑补。
5. **源 Markdown 自身已有说明缺口。** `所属行业`、`所在地区` 的源“字段说明”为空；TSV 的空值属于忠实继承，不能判定为转换丢失。建议后续由客户字段权威源补定义，而不是在 TSV 中猜枚举或地区结构。
6. **展示标签与技术字段未分层。** `客户编号`是面向页面的展示别名，`erpCustomerId`是跨系统主键，`crmCustomerId`是 CRM 外键；当前 16 行结构无法区分这三者，容易造成后续页面或数据模型再次用公司名称关联。

### 2.3 合同管理

对照文件：`合同字段清单.md`（49 个显式字段行）与 `合同字段清单（详细稿）.tsv`（49 行）。

#### P1

1. **类型推断错误会影响失败处理、金额和重试。** `合同金额币种` 被写成 `文本`，但源 Markdown 固定为 `CNY` 且页面为 Select，应为 `单选`；`重试次数` 当前为 `文本`，源规则为非负整数，应为 `数字`；`商机联动失败原因`、`ERP失败原因` 当前为 `单选`，源定义为用户可读失败原因摘要，未给出枚举，应为 `多行文本`或至少普通文本，不能按单选生成。

#### P2

2. **`单选(枚举)`不是线索标准类型值。** 当前用于 `合同状态`、`合同含税标识`、`签署状态`、`签署人来源`、`归档结果`、`作废联动状态`、`OPPORTUNITY_SYNC_STATUS`、`ERP_ORDER_SYNC_STATUS`、`PERFORMANCE_SYNC_STATUS`、`补偿状态` 共 10 个字段。应统一为 `单选`，枚举放在“取值说明”。
3. **“字段说明”49 行全空，但这不是源字段内容被删除。** 合同 Markdown 的字段表本身只有字段名、来源、取值说明、必填性、列表、筛选、详情，没有独立字段说明列；TSV 将其保持为空，取值说明仍在第 12 列。该问题属于详细稿质量和源表结构不足，优先级低于业务字段遗漏。
4. **新增页、编辑页、备注 49 行全空。** 源 Markdown 没有这三列，不能据此推断页面权限或备注。应由 Demo PRD/UI 规则补齐，或明确这些列对合同字段不适用；不能用空值冒充“未定义已确认”。

#### 覆盖与技术字段

49 个显式合同字段均有 TSV 行，外部签署、作废/归档、商机联动、ERP 同步和审计字段没有发现行级遗漏或重复。这里保留为独立字段是合理的：它们是合同结果/审计字段，不是应全部压进“关联客户”等业务字段备注的子字段。源 Markdown 没有定义 `crmCustomerId`/`erpCustomerId` 的合同字段投影，因此本项不能把缺口归因于 TSV 转换。

### 2.4 业绩目标

对照文件：`业绩目标字段清单.md`（75 个字段表行）与 `业绩目标字段清单（详细稿）.tsv`（75 行）。

#### P1

1. **详细字段内容没有从 Markdown 正文规则投影到 TSV。** 75 行的“字段说明”全空；“取值说明”全空；“详情展示”全空；“可筛选”全空；“备注”全空；“新增页/编辑页”也全空。源 Markdown 虽然字段表只有 4 列，但第 20-146 行已经定义了粒度、双状态、事件归属、快照锁定、失败/重试、金额精度和零值规则。当前 TSV 无法单独支持字段级生成和校验，不能直接宣称为详细稿 SSOT。
2. **多项计数/差异/版本/错误字段类型错误。** 计数、金额差异、重试次数和版本号等具体字段见类型错误明细表；这些不是页面展示偏好，而是数据存储与计算语义。
3. **`失败原因`被推成单选，但源没有受控枚举。** 源 Markdown 第 88 行仅定义为“结算任务错误”，应为 `多行文本`或普通文本；失败原因不能由单选控件假定一套未定义枚举。

#### P2

4. **页面列空值主要是源文件未定义，不应臆造。** 新增页、编辑页、列表之外的详情、筛选和备注信息需要从 Demo PRD/UI 规范补齐；字段清单可以暂时留空，但在 TSV 被确认为 SSOT 前必须标注“未定义”或补齐来源。
5. **复合目标值字段的类型无法仅凭现有 Markdown 确认。** `结算快照目标值`、`调整前目标值`、`调整后目标值` 当前为 `文本`，但它们可能是多个目标指标的快照。源未说明是序列化对象、金额还是组合字符串，本审计不把它们强行改成 `数字`或`对象集合`；需要业务确认后再定。

#### 跨系统字段

`CRM 商机ID`、`CRM WON 事件ID`、`CRM WON 时间`、`CRM WON 金额`、`ERP 订单ID`、`ERP 订单确认事件ID`、`ERP 订单确认时间`、`ERP 订单状态`、`ERP 确认订单金额`、`ERP 拆单/合单关联ID`、`ERP 取消/退款金额`、`ERP 修正版本`、`币种`、`含税标识`均保留为独立字段行，没有发现转换阶段的遗漏或重复；问题是这些行的字段说明/取值说明也同样为空。

### 2.5 公海管理

对照文件：`公海字段清单.md`（8 个列表字段行）与 `公海字段清单（详细稿）.tsv`（8 行）。

#### P1

1. **继承字段的类型没有沿用线索标准。** `所属行业` 当前为 `文本`，线索详细稿为 `单选`；`AI评分` 当前为 `文本`，线索详细稿为 `整数`（按本次六类语义可归为数字）；`放弃原因` 当前为 `单选`，线索详细稿为 `多行文本`。公海是线索子视图，不能只继承字段名而丢失类型事实。
2. **源 Markdown 的继承范围与列举表冲突。** 源第 10 行写“继承线索字段清单中列表展示=是的字段，并额外展示”，但第 14-21 行只列了 5 个继承字段和 3 个新增列，未列出线索列表中的联系人、手机号、邮箱、归属人、创建时间、`poolType` 等字段。TSV 复制了列举表，无法判断这是有意的公海精简列，还是转换漏列；在源口径确认前不能作为完整公海列表字段源。

#### P2

3. **页面相关列大量为空。** 8 行中新增页、编辑页、必填性、可筛选、详情展示、取值说明、备注均为空；字段说明只有入池时间、放弃原因和操作列 3 行有值，其余 5 个继承字段因源表说明为空。这主要是源 Markdown 只描述列表展示造成的空值，不能补造新增/编辑/详情规则。
4. **`操作`不是业务字段。** 源定义是“认领按钮”，TSV 以 `文本`字段承载它。建议在详细稿中明确为“列表动作列/非数据字段”，不要让下游把它当作可存储文本字段；当前不把它作为普通数据类型错误处理。

### 2.6 拜访管理

对照文件：

- `拜访计划字段清单.md`：V1.0，文件正文明确写“已废弃”；仅 8 个基础字段。
- `拜访计划字段清单.md_dupe`：V2.0，包含计划、执行、反馈、关联、异常与审计字段。
- `拜访计划字段清单（详细稿）.tsv`：11 行，字段结构与 V1.0 更接近。

#### P0

1. **转换基准与当前源不一致，权威源未收口。** TSV 不是 V2.0 `.md_dupe` 的转换结果，而是沿用已废弃 V1.0 的 8 个字段并额外出现 3 个字段。`.md_dupe` 是否是合并后的新权威源尚未通过规范命名确认；在此状态下，拜访 TSV 不能被确认成唯一字段事实源。

#### P1

2. **若 V2.0 为当前口径，TSV 缺少整组业务字段。** `.md_dupe` 有 63 个 Markdown 表格行；将 `createdBy/createdAt` 与 `updatedBy/updatedAt` 等合并标签展开后约 65 个语义字段，扣除重复的 `feedbackReviewStatus` 后约 64 个唯一字段。TSV 只有 11 行，按表格行至少缺少 52 行，且字段命名体系不一致。缺失范围包括负责人、执行结果、反馈审核、签到定位、反馈内容、下一步行动、对象快照、客户继承 ID、取消/改期/未到访原因、幂等键、操作 ID、审计日志和版本等。
3. **TSV 中 3 个额外字段无法在已废弃 V1.0 源中追溯。** `签到时间`、`签到地址`、`拜访内容`不在 V1.0 Markdown 的 8 个字段中；它们在 V2.0 中有相近但不完全相同的执行字段/反馈字段。当前不能判断这是从其他资料补入、合并产物，还是脚本臆造，应在确定 V2.0 权威源后重新映射。
4. **时间与枚举类型需要标准化。** `拜访状态`使用 `单选(枚举)`，应统一为 `单选`；`计划拜访时间`、`签到时间`的取值包含 `HH:mm`，按线索标准的时间精度应为 `日期时间`，当前 `日期`会丢失“带时间”的类型语义。

#### P2

5. **文件命名和 canonical 路径未收口。** `.md_dupe` 不是可维护的正式文件名，但其 V2.0 内容明显比 V1.0 完整。建议先保留内容并确认 canonical 文件，再由用户确认是否合并/改名/删除；本次不执行任何删除。
