# Forge CRM

> **仓库定位**：Forge CRM 是线索-商机-客户-合同获客 CRM 的**产品知识库 + 前端原型**仓库，不是纯代码工程。结构对齐维他命 QS-JXC-Project 的分层项目框架（01~99 + 版本化），用 `prototype-annotation` 原型标注闭环承接「PRD→页面→评审」。
>
> **开发基线**：`main` 开发、`master` 发布收口（永远最后合并、不直接 push master）；框架里程碑已打 tag `v1-framework-0913`（git 基线，改坏可秒回）。

## 项目简介

Forge CRM 覆盖线索管理、商机管理、客户管理、跟进记录、AI 评分预测五大模块。向上对接 ERP 客户档案与销售订单（客户档案 SSOT 在 ERP），向下串联 WMS 发货履约。核心验证方向：**AI 串联 CRM 和 ERP**，实现线索评分→自动转客户→商机预测→触发销售的闭环。

## 权威源与冲突处理

按信息职责取值，不用一份文档覆盖所有问题：
- 跨模块口径 → `01-全局背景信息/`；跨角色流程 → 业务流程文件；跨单据处理 → 系统单据流程。
- 字段名称/类型/来源/枚举/字段级约束 → **字段清单详细稿 TSV**（确认后为唯一源；初稿只作临时输入）。
- 模块内状态/动作/业务规则/回写/异常 → **业务 PRD**；页面结构/控件/显隐/校验时机/反馈 → **前端 Demo PRD** + `07-UI规范库/`，不反向从 Mock 发明业务规则。
- 冲突先列文件证据+影响范围；未确认的标「待确认」，用户拍板后再同步权威源及受影响下游。AI 生成时发现缺失/冲突先列出，不自行补成已确认事实。

## 文档与变更工作方式（先改权威源，沿依赖往下游传播）

- 字段变化 → 先改详细稿 TSV → 查业务PRD/页面骨架/DemoPRD/原型。
- 状态/动作/业务结果变化 → 先改全局规则/流程/业务PRD → 查字段清单+页面产物。
- 页面布局/控件/反馈变化 → 改 DemoPRD/UI规范/原型，不反向改写业务口径。
- 模板/提示词/方法论变化 → 仅维护对应资产，不批量改写既有业务文档。
- AI 协作：一次只让 AI 输出一个层次；四段式（输入材料/当前任务/权威边界/输出要求）。

## 前端原型开发

- 命令在 `99-产品原型prototype/` 执行：`npm install` / `npm run dev` / `npm run build` / `npm run preview`。
- 技术栈：React + TypeScript + Tailwind CSS v4（CSS-first，token 在 `src/index.css`）+ shadcn 风格组件（`src/components/ui/`）。
- UI 分层、组件复用、命名以 `07-UI规范库/` 与 `src/docs/UI-DESIGN-GUIDE.md` 为准。不提交 node_modules/dist/.env*。

## 验证（分类型质量门，build ≠ 运行态）

- 文档：查相对链接、术语、状态编号、旧口径残留；流程查 Mermaid 语法与闭环。
- 字段清单：查表头/列数、枚举、必填性、引用、下游投影。
- 前端：至少 `npm run build`；页面/路由变化还要 `npm run dev` 人工走查（build 和单测 ≠ 页面运行态）；`data-anno` 标注锚点不被重构清掉。
- 提交：`git diff --check` + 简洁 Conventional Commit（`docs:`/`feat:`/`chore:`）+ git 基线 tag 兜底。

## Git 工作流

- `main` 开发（所有人统一在 main 开发/提交/push）；`master` 收口（永远最后合并，严禁直接 push master）。
- 分支永远一致（main 领先，master 跟随快进）。
- 阶段性完成打 tag（如 `v1-framework-0913`）作 git 基线，改坏可回滚。
